# Validation rules: what the S1 API accepts, and why

This document lists every check the S1 Configuration & Registry API makes before it saves anything. For each rule it says what is allowed, what is refused, and why it matters to the business. It's written for product, business, frontend and QA colleagues as much as for backend engineers.

Collections covered: **users and login**, **categories**, **channels** and **affiliates** (as of 15 Oct 2026). The detailed API contract is [`docs/api/openapi.yaml`](api/openapi.yaml). The decisions behind these rules are in the ADRs:
- [ADR-010](adr/ADR-010-s1-service-conventions.md): conventions;
- [ADR-011](adr/ADR-011-category-identity-and-integrity.md): categories;
- [ADR-013](adr/ADR-013-channel-identity-and-delete.md): channels;
- [ADR-014](adr/ADR-014-affiliate-code-and-pause.md): affiliates;
- [ADR-015](adr/ADR-015-authentication-in-s1.md): login and access;
- [ADR-016](adr/ADR-016-logout.md): logout.

---

## 1. How validation works

**Nothing is saved unless the whole request is valid, and only after we know who is asking.** Checks run in these layers:

| Layer | What it checks | Typical answer |
|---|---|---|
| **0. Who is asking** | A valid login token, and a role allowed to do this | **401** (not logged in, or the token is no longer valid) or **403** (role not allowed) |
| **1. The request itself** | Format, required fields, lengths, ranges, unknown fields | **400**, listing **every** problem at once |
| **2. Business rules against existing data** | Duplicate names, items still used by a campaign, edits based on an old version | **409** (conflict), **412** (outdated version), **404** (not found) |
| **3. Database guarantees** | Unique indexes on names, aliases and codes | The last line of defence. If two people create "Grocery" at the same second, only one succeeds and the other gets 409 |

Every error has the same shape (RFC 9457 "Problem Details"). The UI should branch on `code`; `detail` and `errors[].message` are text for people:

```json
{
  "type": "/problems/validation-failed",
  "title": "Bad Request",
  "status": 400,
  "code": "VALIDATION_FAILED",
  "detail": "2 invalid fields.",
  "instance": "/api/v1/categories",
  "errors": [
    { "field": "name", "message": "Required." },
    { "field": "defaultWindowDays", "message": "Must be a whole number from 1 to 60." }
  ]
}
```

## 2. Rules for every collection

| Rule | What's allowed | Why it matters |
|---|---|---|
| **Logged in** | Every call except login and forgot password needs `Authorization: Bearer <token>`. No token → 401 `AUTHENTICATION_REQUIRED`. A token that's expired, tampered with, logged out, belongs to a disabled user, or was issued before the user's last password change → 401 `INVALID_TOKEN` | Configuration drives campaigns and payouts, so only known colleagues may see or change it |
| **Roles** | Admins create, change and delete; users only read (GET). A user's write → 403 `FORBIDDEN`. The role is read from the database on every call, so a demoted admin loses admin rights at once | PRD S5-01: "an admin writes, a general user reads" |
| **Never cached** | Every API response has `Cache-Control: no-store` (the login response also has `Pragma: no-cache`) | Tokens and business data must never be stored by a browser, proxy or CDN |
| **JSON only** | Request bodies must be JSON objects of at most 100 KB. Any other format → 415 `UNSUPPORTED_MEDIA_TYPE`; broken JSON → 400 `MALFORMED_JSON`; too big → 413 `PAYLOAD_TOO_LARGE`; a JSON list instead of an object → 400 | Keeps out junk and oversized requests. The UI always sends JSON |
| **No unknown fields** | A field the API doesn't know is refused: "Unknown field." | A typo such as `defaultWindowDay` would otherwise be silently ignored, and the user would believe the value was saved |
| **The server owns identity and history** | `id` (and an affiliate's `code`) can't be sent on create ("… is generated by the server.") or changed on edit ("… cannot be changed."). `currentVersionNo`, `createdAt` and `updatedAt` are refused as unknown fields | Campaigns and links point at these values, so they must never be invented or rewritten by a client |
| **Spaces at the ends are removed** | `" Grocery "` is stored as `"Grocery"` | To a user these are the same name; stray spaces would create look-alike duplicates |
| **Names are unique, ignoring letter case** | "Grocery" and "GROCERY" count as the same name → 409 `…_NAME_TAKEN` | A duplicate would split campaigns and reports across two records |
| **Edits change only what is sent** | A PATCH must contain at least one field. Lists (such as aliases) are replaced as a whole | Partial edits are safe, and nothing is cleared by accident |
| **No silent overwrites** | An edit or delete may carry `If-Match: "<version>"` (the `ETag` the user last saw). If someone changed the item since → 412 `VERSION_MISMATCH` and nothing is saved. A malformed `If-Match` → 400 | Two marketers editing the same item can't overwrite each other without knowing |
| **Delete only when unused** | Deleting something a campaign still uses → 409 `…_IN_USE` | A campaign must never point at something that no longer exists |
| **Ids in URLs** | Must be a UUID → otherwise 400. A valid UUID that matches nothing → 404 `…_NOT_FOUND` | Tells a broken link apart from an item that doesn't exist (any more) |
| **Lists are bounded** | `page` is at least 1 (default 1) and `limit` is 1–100 (default 20). Unknown query parameters → 400. Lists are sorted by name, ignoring letter case | Keeps responses fast. A mistyped filter name shouldn't silently return everything |
| **Search** (channels, affiliates) | `?search=` matches text anywhere in the name, ignoring letter case and spaces at the ends. Characters are taken literally, so `/` and `+` mean themselves. A blank search lists everything. Longer than the longest possible name, or sent twice → 400 | The same behaviour as the prototype's search boxes. Literal matching keeps searches safe and fast |

## 3. Categories

*What Marketing promotes (Grocery, Fashion, …). A category gives new campaigns their default attribution window, and maps the Buyer Apps' item categories onto ours.*

| Field | Required? | What's allowed | Why it matters |
|---|---|---|---|
| `name` | **Yes** | 2–100 characters; unique ignoring letter case | Marketing picks categories by name in the campaign wizard and reads them in reports. A duplicate would split campaigns and reports |
| `defaultWindowDays` | No: **7** if omitted | A whole number from 1 to 60 | A campaign's attribution window starts from its category's default, and 7 days is the network default (PRD S1-02). The 1–60 range matches the prototype; Safari's 7-day storage limit makes long windows only partly achievable anyway |
| `aliases` | No: empty if omitted | A list of up to 50 names, each 1–100 characters. Stored trimmed, with repeated spaces collapsed, in lowercase, without duplicates. **An alias can belong to only one category** | Buyer Apps send their own item-category names ("Spices", "Snacks"). Aliases map them onto our category, which makes category match possible (PRD S3-14). If one alias sat in two categories, category match would be ambiguous. Normalising makes "Dry  Fruits" and "dry fruits" the same alias |

**Rules beyond single fields:**
- **Delete** only while no campaign uses the category; otherwise 409 `CATEGORY_IN_USE`.
- **Existing campaigns aren't affected by edits.** A campaign copies the default window when it's created, so changing the category later doesn't change it.

**What the user sees when something is wrong:**

| Request | Answer |
|---|---|
| `{"name": "G"}` | 400 · `name`: "Must be 2 to 100 characters." |
| `{"name": "GROCERY"}` while "Grocery" exists | 409 `CATEGORY_NAME_TAKEN` |
| `{"name": "Toys", "defaultWindowDays": 61}` (also `0` or `7.5`) | 400 · `defaultWindowDays`: "Must be a whole number from 1 to 60." |
| `{"name": "Food", "aliases": ["snacks"]}` while Grocery has "snacks" | 409 `CATEGORY_ALIAS_TAKEN` |
| 51 aliases | 400 · `aliases`: "At most 50 aliases." |
| `{"name": "Food", "aliases": ["  "]}` | 400 · `aliases.0`: "Aliases must not be empty." |
| `DELETE` while a campaign uses the category | 409 `CATEGORY_IN_USE` |

## 4. Channels

*Places where an affiliate posts our tracking link: WhatsApp, Telegram, Instagram, Website / blog, … Each affiliate × channel on a campaign gets its own link, so results can be read per channel (prototype v3).*

| Field | Required? | What's allowed | Why it matters |
|---|---|---|---|
| `name` | **Yes** | 1–50 characters; unique ignoring letter case | One character is enough because "X" is a real channel. 50 keeps chip labels and report columns short. Uniqueness stops "WhatsApp" and "whatsapp" from splitting per-channel results |

**Deliberately not accepted:**
- **`sortOrder`.** It was removed because users couldn't choose a number without knowing every other channel's number. Lists are A–Z instead.
- **A channel code.** The tracking-link format is still being decided (C-S1-07).

Both are refused as "Unknown field."

**Rules beyond single fields:** delete only while no campaign has an affiliate running on the channel; otherwise 409 `CHANNEL_IN_USE`.

**What the user sees when something is wrong:**

| Request | Answer |
|---|---|
| `{"name": "   "}` or a name over 50 characters | 400 · `name`: "Must be 1 to 50 characters." |
| `{"name": "whatsapp"}` while "WhatsApp" exists | 409 `CHANNEL_NAME_TAKEN` |
| `{"name": "SMS", "sortOrder": 1}` | 400 · `sortOrder`: "Unknown field." |
| `GET /channels?search=` with 51 characters | 400 · `search`: "Must be at most 50 characters." |
| `DELETE` while a campaign's affiliate uses the channel | 409 `CHANNEL_IN_USE` |

## 5. Affiliates

*Partner networks (CashKaro, Admitad, Wishlink, …) that spread our tracking links and are paid commission on attributed orders.*

| Field | Required? | What's allowed | Why it matters |
|---|---|---|---|
| `code` | **Set by the server** | Never accepted from users, never changed. Two lowercase letters from the name, then 4 characters with no vowels and no look-alikes: `ckB7XQ` for CashKaro | Tracking links contain the code. Once a link is posted it can't be called back, so the code stays the same even if the affiliate is renamed (team decision, ADR-014). Without vowels a code can't spell a word in a public link; without look-alikes (0/O, 1/I/L) it can't be misread |
| `name` | **Yes** | 2–100 characters; unique ignoring letter case | Marketing picks affiliates by name in the wizard and reads them in reports |
| `contactEmail` | No | A valid email of at most 254 characters, stored lowercase. A blank value or `null` means "no email" | Prefills the recipients when Marketing sends the affiliate its report (PRD S4-23). Lowercase avoids two spellings of one address |
| `defaultCommissionRatePercent` | **Yes** | Above 0 and at most 100, with up to 2 decimals (6, 6.5, 7.25) | Every affiliate on a campaign needs a commission rate (PRD S1-03), and this default prefills it. As the prototype says, without a rate "there is no cost side and no ROI". Two decimals match how rates are quoted |
| `defaultContractWindowDays` | No: **14** if omitted | A whole number from 1 to 60 | The contract window decides which conversions go into the affiliate's report (PRD S3-13, S4-22). 14 days is the prototype's default, and 60 matches the attribution-window bound. Tell the team if a contract needs longer |
| `status` | **Set by the server** on create (`active`) | On edit: `active` or `paused` | **Pause** = the affiliate can't be added to new campaigns, while campaigns it's already on keep running. **Resume** = selectable again. A new affiliate is always active, so status can't be sent on create |

**Rules beyond single fields:**
- **Defaults prefill campaigns.** The commission rate and contract window are copied into each campaign when the affiliate is added. Changing a default later never changes existing campaigns (enforced in the campaigns task).
- **Delete** only while no campaign has the affiliate; otherwise 409 `AFFILIATE_IN_USE`. To retire an affiliate that has history, **pause** it instead.
- **The list** can also be filtered with `?status=active` or `?status=paused`. The campaign wizard asks for active affiliates only.

**What the user sees when something is wrong:**

| Request | Answer |
|---|---|
| `{}` | 400 · `name`: "Required." · `defaultCommissionRatePercent`: "Required." |
| `{"name": "CashKaro", "defaultCommissionRatePercent": 0}` (also `-1`, `100.5`, `6.333`) | 400 · "Must be a number above 0 and at most 100, with up to 2 decimals." |
| `"defaultContractWindowDays": 61` (also `0` or `7.5`) | 400 · "Must be a whole number from 1 to 60." |
| `"contactEmail": "ops-at-cashkaro.com"` | 400 · "Must be a valid email address." |
| `"code": "ckAB14"` on create / on edit | 400 · "code is generated by the server." / "code cannot be changed." |
| `"status": "paused"` on create | 400 · "A new affiliate is always active; pause it afterwards with PATCH." |
| `{"status": "deleted"}` on edit, or `?status=deleted` | 400 · "Must be active or paused." |
| `{"name": "CASHKARO"}` while "CashKaro" exists | 409 `AFFILIATE_NAME_TAKEN` |
| `DELETE` while a campaign has the affiliate | 409 `AFFILIATE_IN_USE` (pause it instead) |

## 6. Users and login

*The people who can log in to the Marketing UI. An **admin** changes configuration and manages users; a **user** reads configuration (PRD S5-01).*

| Field | Required? | What's allowed | Why it matters |
|---|---|---|---|
| `email` | **Yes** | A valid email of at most 254 characters, stored lowercase; unique | It's the login name. Lowercase means "Ravi@ONDC.org" and "ravi@ondc.org" are the same account |
| `name` | **Yes** | 2–100 characters | Shown in history: who changed what |
| `role` | **Yes** | `admin` or `user` | Decides who may change configuration |
| `password` | **Yes** (on create) | The password rules below | The admin shares it with the person manually |
| `status` | Set by the server (`active`); on edit `active` or `disabled` | A disabled user can't log in, and any token they hold stops working at once | Colleagues who leave lose access immediately. Users are never deleted, because history needs them |
| `id`, `failedAttempts`, `lockedUntil`, `createdBy`, `passwordChangedAt`, `lastLoginAt`, `currentVersionNo`, `createdAt`, `updatedAt` | Set by the server | Never accepted from the client | Identity and history must be trustworthy |

**Password rules:** they apply to new accounts, to changing your own password and to forgot password.
- At least **8** characters.
- At least one **uppercase** letter (A–Z), one **lowercase** letter (a–z), one **digit** (0–9) and one **symbol**: any character that isn't a letter, digit or space, such as `@ # $ % !`.
- At most 64 characters and 72 bytes. That's a technical limit, because bcrypt ignores anything longer.
- Each rule that fails gets its own message, so the user sees everything to fix at once.
- Passwords are stored only as a bcrypt hash, never as text, and never appear in any response.

**Rules beyond single fields:**
- **Login:**
  - A wrong email, a wrong password and a disabled account all get the **same** 401 `INVALID_CREDENTIALS`, so nobody can find out which emails have accounts.
  - **5 wrong passwords in a row** lock the account for **15 minutes**: 423 `ACCOUNT_LOCKED`, with `Retry-After`. A successful login resets the count.
- **Changing your own password** needs the current one. A wrong current password is 400 on `currentPassword` and counts towards the lockout. Afterwards you log in again, because older tokens stop working.
- **Forgot password** (email + new password, no login needed) sets the new password and clears a lockout. ⚠ It has **no verification yet**: an accepted risk until email is available (ADR-015).
- **Logout** (`POST /auth/logout`) is open to any signed-in user, whatever their role.
  - The token it's sent with is refused from then on: 401 `INVALID_TOKEN`.
  - The user's other sessions continue. To end every session, change the password.
- **The last active admin** can't be disabled or made a user: 409 `LAST_ADMIN`.

**What the user sees when something is wrong:**

| Request | Answer |
|---|---|
| Login with a wrong password, an unknown email or a disabled account | 401 `INVALID_CREDENTIALS` · "The email or password is incorrect." |
| The 5th wrong password in a row | 423 `ACCOUNT_LOCKED` · "Too many wrong passwords. Try again in 15 minutes." |
| `"password": "password"` | 400 · "Must contain at least one uppercase letter (A–Z)." · "… one digit (0–9)." · "… one symbol, such as @ # $ % or !." |
| `"password": "Ab1@"` | 400 · "Must be at least 8 characters." |
| `{"role": "superadmin"}` | 400 · "Must be admin or user." |
| `{"email": "RAVI@ondc.org"}` while ravi@ondc.org exists | 409 `USER_EMAIL_TAKEN` |
| A user calling POST /categories or /users | 403 `FORBIDDEN` · "Your role doesn't allow this. Ask an admin." |
| Disabling the only active admin | 409 `LAST_ADMIN` |
| Forgot password for an email with no active account | 404 `USER_NOT_FOUND` |
| Any call without a token / with an expired token | 401 `AUTHENTICATION_REQUIRED` / 401 `INVALID_TOKEN` |
| Any call with a token that was logged out, including a second logout | 401 `INVALID_TOKEN` |

## 7. Error codes at a glance

| HTTP | `code` | When | What the user can do |
|---|---|---|---|
| 400 | `VALIDATION_FAILED` | One or more fields, query parameters, the id or `If-Match` are invalid. `errors[]` lists each one | Fix the listed fields and resend |
| 400 | `MALFORMED_JSON` | The body isn't valid JSON | A bug in the caller: fix the request |
| 401 | `AUTHENTICATION_REQUIRED` | No login token was sent | Log in |
| 401 | `INVALID_TOKEN` | The token is expired or invalid, it was logged out, the user was disabled, or the password changed after the token was issued | Log in again |
| 401 | `INVALID_CREDENTIALS` | Login: wrong email or password, or a disabled account | Check the email and password, or ask an admin |
| 403 | `FORBIDDEN` | The user's role isn't allowed to do this | Ask an admin |
| 404 | `CATEGORY_NOT_FOUND`, `CHANNEL_NOT_FOUND`, `AFFILIATE_NOT_FOUND`, `USER_NOT_FOUND` | No item has this id (deleted, or never existed); for forgot password, no active account has the email | Refresh the list, or check the email |
| 404 | `ROUTE_NOT_FOUND` | The URL doesn't exist | Check the URL |
| 405 | `METHOD_NOT_ALLOWED` | The method isn't supported on this URL; the `Allow` header lists the ones that are | Use one of the allowed methods |
| 409 | `CATEGORY_NAME_TAKEN`, `CHANNEL_NAME_TAKEN`, `AFFILIATE_NAME_TAKEN` | Another item already has this name, ignoring letter case | Choose another name, or use the existing item |
| 409 | `CATEGORY_ALIAS_TAKEN` | The alias already belongs to another category | Remove it from the other category first, or drop it |
| 409 | `CATEGORY_IN_USE`, `CHANNEL_IN_USE`, `AFFILIATE_IN_USE` | A campaign still uses the item | Keep it; for an affiliate, pause it instead |
| 409 | `USER_EMAIL_TAKEN` | Another user already has this email | Use another email, or edit the existing user |
| 409 | `LAST_ADMIN` | The change would leave no active admin | Make someone else an admin first |
| 412 | `VERSION_MISMATCH` | Someone changed the item after the user loaded it | Reload the item and make the change again |
| 413 | `PAYLOAD_TOO_LARGE` | The body is larger than 100 KB | Send less data |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | The body isn't sent as JSON | Send `Content-Type: application/json` |
| 423 | `ACCOUNT_LOCKED` | 5 wrong passwords in a row; `Retry-After` gives the seconds left | Wait 15 minutes, or use forgot password |
| 500 | `INTERNAL_ERROR` | An unexpected error; no internal details are returned, and the server logs it | Retry; report it if it continues |
| 503 | `SERVICE_UNAVAILABLE` | The database can't be reached | Retry shortly |

## 8. Not checked yet (known gaps)

| Gap | Why it's not checked yet | When |
|---|---|---|
| ⚠ **That a forgot-password request really comes from the account's owner** | There's no email or SMS yet to send a code or link to. Anyone who knows a colleague's email can set a new password for them. The 404 for an unknown email also shows which emails have accounts. This is an **accepted risk** (ADR-015) | **Before production**, with ONDC's mail relay |
| Login history, rate limiting by IP address, multi-factor authentication | Not needed for the first phase | Later |
| How S2–S4 check tokens and learn about logouts; the final token lifetime and refresh | Cross-service decisions. S1 itself refuses a logged-out token (ADR-016) | The multi-service work |
| **Why** something changed (a mandatory reason, PRD S1-09) | Comes with version history and rollback | The versioning task |
| A paused affiliate can't be added to a campaign; each affiliate on a campaign needs at least one channel and a commission rate | These are rules about campaigns | The campaigns task |
| A delete happening at the same moment a campaign starts using the item | Closing this needs a database transaction | The campaigns task |
| Whether a category's own name counts as a match, alongside its aliases | A category-match (S3) decision | The S3 work |

## 9. For engineers: where each rule lives

| What | Where |
|---|---|
| Who is asking (token, logged out, active user, password changed since) and roles | `src/middlewares/authenticate.js`, `src/middlewares/authorize.js`, `src/services/token.service.js`, `src/services/auth.service.js`, `src/repositories/revokedToken.repository.js` |
| Password rules, hashing and lockout | `src/validators/user.validator.js`, `src/utils/password.js`, `src/services/auth.service.js` |
| Limits (lengths, ranges, defaults), shared by the validator and the model | `src/constants/<resource>.constants.js` |
| Request checks and their messages | `src/validators/<resource>.validator.js`, built from the shared pieces in `src/utils/validation.js` |
| Second guard at the database (types, ranges, unique indexes, `immutable` code) | `src/models/<resource>.model.js` |
| Business rules (defaults, code generation, "in use", version checks) | `src/services/<resource>.service.js` |
| Turning database conflicts into 409s | `src/repositories/<resource>.repository.js` |
| Generic checks (JSON only, body size, unknown routes and methods) | `src/app.js`, `src/middlewares/validate.js`, `src/middlewares/errorHandler.js` |

**When a rule changes:**
1. Change the constant.
2. Update the tests in `tests/integration/`.
3. Update `docs/api/openapi.yaml` and **this document**.
