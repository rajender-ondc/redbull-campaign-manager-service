# ADR-009: MongoDB with Mongoose for S1

- **Status:** Accepted, 13 Oct 2026
- **Service:** S1 Configuration & Registry ("campaign manager")
- **Numbering:** ADR-001…008 live in the draft architecture PDF; this repo continues from 009.

## Context

S1 stores everything Marketing configures: categories, Buyer Apps, affiliates, channels, campaigns, and later config versions and snapshots (see `docs/data_model-S1`). This data:
- is shaped like documents (a campaign holds arrays of Buyer Apps and affiliates);
- is written rarely, by admins;
- is versioned as whole items (`config_versions.content` is "the whole item").

Each service owns its own store (draft ADR-003), and the team has chosen MongoDB for S1. We also need a way for Node.js code to talk to MongoDB.

## Decision

- **MongoDB is S1's only data store.** No other service reads it directly.
- **Data access goes through Mongoose 9:**
  - the schema and indexes are declared next to each model;
  - primary keys are UUIDs, stored as BSON UUID in `_id` and generated by the app with Node's `crypto.randomUUID()`;
  - `createdAt` / `updatedAt` timestamps come from Mongoose (camelCase fields, per the team naming standard in ADR-010);
  - `sanitizeFilter` is on, as a second guard against query-operator injection.
- **Only `src/repositories/` uses Mongoose** (see ADR-010). Services and controllers never build queries.
- **Database rules are enforced by the database where it can.** Unique indexes enforce uniqueness, and the code turns duplicate-key errors into clean 409 responses rather than checking first and then writing.

## Alternatives considered

- **Native MongoDB driver without Mongoose.** Thinner, but we'd hand-write schema definitions, index declarations, timestamps and type casting.
- **A relational database (PostgreSQL).** It has real foreign keys, but the team chose MongoDB, and S1's data maps naturally to documents.

## Consequences

**Good:**
- Whole-item documents fit `config_versions.content` directly.
- Unique indexes guarantee unique names and aliases even under concurrent requests.

**To handle later:**
- **Transactions need a replica set.** The local MongoDB 9.0.2 is standalone, and multi-document transactions require a replica set. The versioning task (writing `config_versions`, `publish_seq` and the item in one transaction) will need one, and tests will need `mongodb-memory-server`'s replica-set mode.
- **There are no foreign keys.** Rules such as "a category is used by a campaign" are checked in code (`isInUse`), which leaves a small race; ADR-011 records it.
- **Production index builds.** Mongoose builds indexes automatically on start-up (`autoIndex`), which is fine for development and tests. Production needs an explicit index-build step at the first deployment.
