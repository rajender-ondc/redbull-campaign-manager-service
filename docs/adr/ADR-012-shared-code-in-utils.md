# ADR-012: Shared code lives in `src/utils/`; each resource keeps its own layers

- **Status:** Accepted, 14 Oct 2026
- **Service:** S1 Configuration & Registry
- **Amends:** ADR-010 §1. That section said `utils/` would be created only when first needed; it's needed now.

## Context

Channels are the second resource, after categories. Both need the same five operations:
- create;
- list;
- get one;
- change, with a version check;
- delete while unused.

A plain copy of the category files would repeat the same mechanics:
- `id`, `If-Match` and paging validation;
- the `_id` → `id` mapping;
- the version-checked update and delete;
- the `{ data }` response with `ETag` and `Location`;
- the 404, 409 and 412 errors.

`rules.md` asks for no duplicate code and clean code, without over-complication. We weighed three shapes (see Alternatives). The team chose to keep the category pattern for every resource and to move only code that is genuinely common into `utils/`. The reason: two resources that look alike today can have different business rules tomorrow.

## Decision

1. **Every resource keeps its own six layers.** These are route, validator, controller, service, repository and model, plus a constants file, just as categories have them. Those files hold everything that has business meaning:
   - field limits and defaults;
   - list order;
   - which unique index means which conflict;
   - what blocks a delete;
   - the endpoints themselves.
2. **Code moves to `src/utils/` only when both of these are true:**
   - at least two resources use it;
   - it has no business meaning: it's an API convention or a database mechanic.
3. **Shared error builders live next to `ApiError`** in `src/errors/ApiError.js`, because that's where a developer looks for errors.

| Module | What it holds | Who uses it |
|---|---|---|
| `src/utils/validation.js` | Zod building blocks: the UUID `id` path parameter; `If-Match` → `expectedVersion`; the `page` / `limit` query; "the body must be a JSON object"; the `id` guards ("generated by the server" on create, "can't be changed" on update), and the same guards for other server-owned fields such as an affiliate's `code`; builders for a name field, the `?search=` parameter, and create and update bodies | validators |
| `src/utils/mongo.js` | The `CASE_INSENSITIVE` collation; `_id` → `id`; the duplicate-key check; the "name contains" search pattern; reading one page of documents, optionally filtered; the version-checked update and delete | models, repositories |
| `src/utils/response.js` | 201 with `Location` and `ETag`; 200 with `ETag`; a list page with its `pagination` block | controllers |
| `src/errors/ApiError.js` | `ApiError` plus builders for: not found (404), name taken (409), in use (409), version mismatch (412), and why a conditional write matched nothing (404 or 412) | services, repositories |

**Error codes** are built from the resource name: "channel" gives `CHANNEL_NOT_FOUND`, `CHANNEL_NAME_TAKEN` and `CHANNEL_IN_USE`. Clients rely on the code; `detail` is text for humans.

## Alternatives considered

| Option | Why not |
|---|---|
| Copy the category files for every resource | Every resource would repeat the same 404/412/409, paging and ETag code, and every fix would have to be made everywhere |
| Generic factories (one `createCrudService`, one `createCrudRepository`, … configured per resource) | Less code, but each resource's rules end up spread across hooks. That's harder for a new engineer to follow, and harder to change for one resource only |
| One engine that generates the routes from a config object | No file shows which endpoints exist. It also won't fit campaigns or Buyer Apps, which have lifecycles and nested data |

## Consequences

- **A new resource only writes what's special about it.** The conventions (envelope, ETag, errors, paging) stay identical by construction.
- **Changing a convention is a one-file change.** For example, adding a field to every success response.
- **Resource files still share a shape** (each has `create`, `getById`, …). That's deliberate: they're where each resource's own rules live.
- **`utils/` must never collect business rules.** A helper that needs to know about one specific resource belongs in that resource's files.
- **One message changed wording** when categories moved onto the shared builders:
  - The 409 for a taken name now reads: *The name "X" is already used by another category (names are compared ignoring letter case).*
  - That works for every resource; "A category named …" would need "an" for resources like "affiliate".
  - The code `CATEGORY_NAME_TAKEN` is unchanged.
